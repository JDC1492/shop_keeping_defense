# vulnlab

> **WARNING: this application is deliberately vulnerable.**
> Run it only on localhost or inside Docker on your own machine. Never deploy it to a public
> network, a shared server, or any cloud environment. Use fake data only, and never reuse real
> credentials, tokens, or secrets anywhere in this repo.

A small Rails API + React app with planted security and accessibility flaws, built to practice a
**find it → automate it → fix it** cycle:

1. **Security** exploits a flaw and documents it in `findings/`.
2. **QA** writes a Playwright test (and the dev adds an RSpec spec) that asserts the *secure* behavior, so it fails on the vulnerable build.
3. **Dev** fixes the flaw; both tests flip to green.
4. **Security** re-tests manually and signs off.

## Who owns what

| Role | Owns | Day-to-day |
|---|---|---|
| **Dev** | `api/`, `web/`, `api/spec/` | Builds the app, plants flaws, ships fix PRs, writes RSpec request specs |
| **Security** | `findings/`, `poc/` | Finds and documents exploits, verifies fixes |
| **QA** | `e2e/`, `.github/`, `docs/CONVENTIONS` in `WORKFLOW.md` | Playwright (TypeScript) API, browser and axe-core a11y tests; CI; test conventions |

## Repo layout

```
vulnlab/
├── api/                      Rails API (generated by the dev; see docs/BOOTSTRAP.md)
│   └── spec/                 RSpec request specs, support helpers, factories
├── web/                      React frontend (generated by the dev)
├── e2e/                      Playwright + TypeScript (QA)
│   ├── tests/api/            API-level exploit regressions
│   ├── tests/browser/        Browser-level security tests (XSS, UI access control)
│   ├── tests/a11y/           axe-core accessibility scans
│   ├── fixtures/             Authenticated API contexts for seeded users
│   └── support/              Seed users, open-findings reader
├── findings/                 One markdown file per finding + open-findings.json + index
├── docs/                     API contract, workflow, bootstrap steps
├── .github/                  CI workflow and PR template
└── docker-compose.yml        db + api + web, bound to 127.0.0.1 only
```

## How a finding flips from red to green

`findings/open-findings.json` is the single source of truth for which findings are still open.
Both suites read it:

- While a finding is listed there, its tests are **expected to fail** (`test.fail()` in Playwright, `pending` in RSpec). CI stays green and meaningful.
- The fix PR removes the ID from the file. The tests now run as normal and must pass.
- If a dev fixes the bug but forgets to remove the ID, the "expected to fail" tests *pass* and CI goes red. Nobody can quietly fix something without updating the record.

## Quickstart (once the app exists)

```bash
docker compose up --build -d
docker compose exec api bin/rails db:seed

# Playwright
cd e2e
npm ci
npx playwright install chromium
npx playwright test            # everything
npx playwright test --project=api
npx playwright test --project=a11y
npx playwright show-report

# RSpec
docker compose run --rm -e RAILS_ENV=test api bundle exec rspec
```
